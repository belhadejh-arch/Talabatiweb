MANDATORY — FINAL DRIVER EMAIL ORDER SYSTEM

عدّل المشروع الحالي فقط. لا تعِد بناء المشروع، ولا تحذف أو تغيّر أي ميزة أو تصميم أو بيانات غير مرتبطة بهذه المهمة. يجب تنفيذ جميع النقاط فعلياً، بدون Mock Data أو Demo Data أو LocalStorage.

الهدف النهائي:

الزبون ينشئ الطلب
→ يتم حفظه في PostgreSQL
→ يتم تحديد المطعم
→ يتم تحديد السائق النشط التابع للمطعم
→ يتم إرسال الطلب إلى البريد الإلكتروني للسائق
→ السائق يقبل أو يرفض من البريد
→ يتم تحديث PostgreSQL
→ يظهر الطلب تلقائياً في تطبيق السائق
→ يتم حفظه في السجل والإحصائيات والأرباح.

==================================================
1. السائق والبريد الإلكتروني
==================================================

عند إضافة أو تعديل سائق في لوحة الإدارة يجب وجود:

- اسم السائق.
- رقم الهاتف.
- البريد الإلكتروني.
- المطعم المرتبط.
- الحالة: نشط / غير نشط.

البريد الإلكتروني إلزامي وصحيح.

كل سائق له بريد إلكتروني خاص به، وهذا البريد هو الوسيلة الوحيدة التي تصل إليها طلباته.

عند تغيير بريد السائق:
- استخدم البريد الجديد للطلبات القادمة.
- لا تغيّر الطلبات التاريخية.

عند تغيير مطعم السائق:
- يتوقف عن استقبال طلبات المطعم القديم.
- يبدأ استقبال طلبات المطعم الجديد فقط بعد أن يكون نشطاً.
- لا تغيّر المطعم في الطلبات التاريخية.

==================================================
2. Gmail SMTP
==================================================

استخدم Gmail SMTP من Backend فقط:

SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER
SMTP_PASS

SMTP_PASS هو Gmail App Password وليس كلمة مرور Gmail العادية.

استخدم Nodemailer أو مكتبة SMTP الموجودة في المشروع.

ممنوع:
- وضع بيانات SMTP في Frontend.
- وضع الأسرار داخل Git أو الكود.
- إظهار SMTP_PASS.
- تسجيل كلمات المرور أو الأسرار في Logs.

==================================================
3. إرسال الطلب للسائق
==================================================

بعد إنشاء الطلب وحفظه بنجاح في PostgreSQL:

1. تحقق من المطعم والعضوية.
2. ابحث عن السائقين النشطين المرتبطين بنفس المطعم.
3. اختر السائق الحالي حسب نظام التوزيع التسلسلي الموجود.
4. أرسل البريد إلى السائق الحالي فقط.
5. لا ترسل الطلب إلى جميع السائقين.
6. لا ترسل إلى سائق غير نشط.
7. لا ترسل إلى سائق تابع لمطعم آخر.

لا يتم إرسال البريد بسبب:
- تحديث الصفحة.
- تسجيل الدخول.
- إعادة تشغيل Backend.
- فتح تطبيق السائق.
- الطلبات القديمة.
- أي بيانات تجريبية.

==================================================
4. نظام توزيع الطلبات
==================================================

حافظ على نظام التوزيع التسلسلي:

- أول سائق نشط ومؤهل يستقبل الطلب.
- إذا قبل الطلب، يتوقف التوزيع ويثبت الطلب عليه.
- إذا رفض، ينتقل الطلب للسائق النشط التالي لنفس المطعم.
- إذا لم يرد خلال 5 دقائق، تصبح المحاولة TIMEOUT وينتقل الطلب للسائق التالي.
- لا يعاد إرسال الطلب إلى سائق رفضه سابقاً.
- لا يعاد إرسال الطلب إلى سائق انتهت مهلة محاولته.
- المهلة تعمل من Backend وليس من Frontend.
- يجب أن تستمر المهلة حتى عند إغلاق التطبيق أو الصفحة أو إعادة تشغيل الخادم.

يجب منع Race Conditions والقبول المزدوج باستخدام PostgreSQL Transactions / Atomic Operations.

==================================================
5. محتوى البريد
==================================================

كل بريد طلب يجب أن يحتوي على:

- رقم الطلب الحقيقي.
- اسم المطعم.
- نوع الطلب: توصيل / حجز.
- اسم الزبون.
- رقم الهاتف.
- المنتجات.
- الكميات.
- أسعار المنتجات.
- الإجمالي بالدينار الليبي.
- ملاحظات الزبون.
- التاريخ.
- الوقت.

إذا كان الطلب توصيلاً:

- Latitude الحقيقي.
- Longitude الحقيقي.
- رابط Google Maps مبني على الإحداثيات.
- لا يتم اعتماد طلب التوصيل إذا كان الموقع الإلزامي مفقوداً.

إذا كان الطلب حجزاً:

- اسم الزبون.
- الهاتف.
- تفاصيل الحجز.
- تفاصيل الطلب.
- التاريخ والوقت.
- الملاحظات.

==================================================
6. قبول ورفض الطلب من البريد
==================================================

أضف داخل البريد:

[ قبول الطلب ]

[ رفض الطلب ]

كل رابط يجب أن يكون آمناً ومربوطاً بـ:

order_id
assignment_id
driver_id
secure token

عند الضغط على أي زر يجب على Backend التحقق من:

- السائق الصحيح.
- الطلب الصحيح.
- Assignment الصحيح.
- أن Assignment ما زال PENDING.
- أن الطلب لم يقبله سائق آخر.
- أن المهلة لم تنتهِ.
- أن الرابط صالح ولم يستخدم سابقاً.

عند القبول: - Assignment = ACCEPTED.
- Order = ACCEPTED.
- تسجيل السائق.
- تثبيت الطلب للسائق.
- إيقاف التوزيع.
- تحديث PostgreSQL.
- إظهار العملية في تطبيق السائق.

عند الرفض:

- Assignment = REJECTED.
- تسجيل الرفض.
- إيقاف صلاحية أزرار البريد القديمة.
- الانتقال للسائق التالي.
- إرسال البريد للسائق التالي فقط.

عند انتهاء 5 دقائق:

- Assignment = TIMEOUT.
- تسجيل العملية.
- الانتقال للسائق التالي.

الإيميل هو فقط وسيلة وصول الطلب للسائق.

لا تضف أي نظام إشعارات داخل التطبيق.

ممنوع:

- OneSignal.
- Telegram.
- Push Notifications.
- Web Push.
- إشعارات صوتية.
- Popup إشعارات جديدة.

13. فشل البريد وإعادة المحاولة
==================================================

إذا فشل SMTP:

- سجل الخطأ.
- اجعل الحالة FAILED.
- أعد المحاولة بشكل آمن.
- لا تنشئ Order جديداً.
- لا تنشئ Assignment جديداً.
- لا تغير السائق إلا وفق نظام التوزيع الفعلي.
- لا ترسل نسخة مكررة بعد نجاح الإرسال.

يجب أن يكون إرسال البريد Idempotent.     ==================================================

GMAIL SMTP — بيانات الإرسال التي سأوفرها
==================================================

سأوفر لك بيانات Gmail المخصصة لإرسال طلبات السائقين:

- بريد Gmail المرسل.
- Gmail App Password مكونة من 16 حرفاً.

استخدم هذه البيانات فقط لإرسال الطلبات عبر Gmail SMTP.

يجب وضعها في Environment Variables في Backend/Render فقط:

SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=البريد الذي سأوفره
SMTP_PASS=App Password التي سأوفرها

مهم جداً:
- SMTP_PASS هي Gmail App Password المكونة من 16 حرفاً، وليست كلمة مرور Gmail العادية.
- لا تضع البريد أو كلمة المرور داخل ملفات المشروع أو Git.
- لا ترسل SMTP_PASS إلى Frontend.
- لا تظهر SMTP_PASS في لوحة الإدارة أو Logs أو API Responses.
- لا تطبع كلمة المرور أثناء الاختبارات.
- استخدم SMTP_USER وSMTP_PASS من Environment Variables فقط.
- استخدم البريد المحدد في SMTP_USER كعنوان الإرسال لجميع طلبات السائقين.
- جميع رسائل الطلبات تخرج من هذا البريد المركزي إلى البريد الإلكتروني المسجل لكل سائق.
- لا يحتاج كل سائق إلى Gmail SMTP خاص به؛ السائق يحتاج فقط إلى بريده الإلكتروني لاستقبال الطلبات.

بعد إضافة المتغيرات، اختبر SMTP فعلياً بإرسال رسالة اختبار إلى بريد سائق موجود، ثم اختبر طلباً حقيقياً.

إذا فشل الاتصال بـ SMTP، اعرض الخطأ التقني في Backend Logs بدون كشف كلمة المرور، وأصلح المشكلة قبل اعتبار النظام مكتملاً.


نفّذ التعديلات فعلياً داخل المشروع، وليس مجرد شرح أو اقتراح. افحص الملفات الحالية قبل التعديل، حافظ على البيانات الموجودة، أصلح جميع الأخطاء الناتجة، وشغّل الاختبارات اللازمة. في النهاية اذكر الملفات التي تم تعديلها، الـMigrations التي تمت إضافتها، ومتغيرات Render المطلوبة دون كشف أي أسرار.
